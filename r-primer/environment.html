R, RStudio, and Your Environment


26 minutes

This chapter is the unglamorous one. It is also the one that decides whether the next fourteen weeks are spent thinking about data or fighting your own laptop.

Nearly every setup problem I see in this course comes from one of four things: not knowing where R thinks it is, not knowing which copy of an object is real, not knowing whether a package is installed or merely loaded, and having a session so full of accumulated state that nothing can be trusted. All four are avoidable with habits that take a week to build.

R and RStudio are two different programs

R is the language and the engine. It is what actually computes. If you launch R directly you get a bare prompt, and everything works.

RStudio is an integrated development environment—an editor, a file browser, a plot viewer, a help viewer, and a console, arranged around R. It does not compute anything itself; it drives R. You can replace RStudio with VS Code or Positron and nothing about your analysis changes.

Two practical consequences. First, install R before RStudio, because RStudio looks for an R installation when it starts. Second, when something goes wrong, ask which of the two is at fault. “My plot does not appear” is usually RStudio. “My mean is NA” is never RStudio.

Install both from the links in the syllabus. Take the current release of each; there is no reason to pin an old version for this course. Then check that R is what you think it is:

R.version.string
#> [1] "R version 4.5.0 (2025-04-11)"

If that prints something from several years ago, you have an old R that RStudio found first. Update it before term starts rather than during a lab.

The four panes

RStudio opens with a console and grows three more panes once you open a file. What each is for matters more than where it sits.

  • Source (top-left). Your scripts and RMarkdown documents. This is the permanent record.
  • Console (bottom-left). Where R actually runs. Transient.
  • Environment / History (top-right). Every object currently in memory. Worth glancing at constantly.
  • Files / Plots / Packages / Help (bottom-right). Where plots and documentation land.

Two keyboard shortcuts pay for themselves in the first week:

Action macOS Windows/Linux
Send current line/selection to console Cmd+Enter Ctrl+Enter
Insert <- Option+- Alt+-
Restart R Cmd+Shift+F10 Ctrl+Shift+F10
Insert code chunk (RMarkdown) Cmd+Option+I Ctrl+Alt+I

That third one is the important one, and we will come back to it.

Console versus script

This is the distinction that trips up the most people, so it is worth stating flatly.

The console changes the state of your session. The script is the record of how that state was reached.

Both create real objects. An object made in the console is exactly as usable as one made by a script—R does not label them. The difference is that the console leaves no trace in any file. Three hours later your analysis works beautifully and your script, taken on its own, does not run.

You will not notice, because from inside your session everything is fine. Your teammate will notice. So will you, in November, when you reopen the project.

The rule: the console is for looking, the script is for doing. Type head(dat) and summary(dat$age) and nrow(dat) in the console freely—those inspect, they do not create. The moment you write <-, it belongs in the script. Write it there and send it down with Cmd/Ctrl+Enter.

Works on My Machine

Your script runs perfectly in your RStudio session. You push it to your team’s repository and a teammate reports that line 40 fails with object 'threshold' not found.

You open the script, search it, and confirm: the word threshold appears on line 40 and nowhere else.

What most likely happened?

You typed threshold <- ... in the console and never moved it into the script.

This is the single most common failure in a first data science course, and it will happen to you. The console and the script are two different things: the console changes the state of your session, the script is the record of how that state was reached. An object created in the console is just as real as one created by the script—your later lines find it and work perfectly—but it exists nowhere in the file you handed over.

Your session and your script have quietly diverged, and nothing warns you, because from inside the session everything works.

The other options are not plausible. No version of R invents variables; source() evaluates in the global environment by default and does not conjure missing objects; and Git transfers files byte for byte—if a line were missing you would see it in git diff.

The fix is a habit, not a tool. Restart R and run the script from the top, regularly, and certainly before you push. In RStudio that is Session → Restart R (Cmd/Ctrl+Shift+F10), which empties the environment, followed by Source. If it runs clean from an empty environment, it will run for your teammate.

The related setting: in Tools → Global Options, turn off “Restore .RData into workspace at startup” and set “Save workspace to .RData on exit” to Never. Otherwise R helpfully reloads yesterday’s objects at every launch, and you can go weeks without discovering that your script has not actually worked since Tuesday.

Where R thinks it is

R has a working directory: the folder that relative file paths are interpreted against.

getwd()
#> [1] "/Users/dana/projects/transit-analysis"

If the working directory is that folder, then read.csv("data/rides.csv") looks for /Users/dana/projects/transit-analysis/data/rides.csv. Simple enough. The trouble starts with how people set it.

The instinctive move—and the one you will see in older tutorials and in AI-generated scripts—is:

setwd("/Users/dana/Desktop/project final v3")   # do not do this

That line works on exactly one computer. It fails for your teammate, it fails for me when I grade it, and it fails for you when you get a new laptop. It is the single most common reason a submitted analysis does not run.

Use a Project instead

An RStudio Project is a folder with a .Rproj file in it. When you open the project—by double-clicking the .Rproj, or via File → Open Project—RStudio starts a fresh R session with the working directory already set to that folder.

Create one now: File → New Project → New Directory → New Project, and give it a name with no spaces in it.

Because the working directory is handled for you, every path in your code can be written relative to the project root, and those paths work on every machine that has the folder:

dat <- read.csv("data/rides.csv")
saveRDS(model, "output/model.rds")

A layout that scales, and that I would like to see in your project repositories:

transit-analysis/
├── transit-analysis.Rproj
├── README.md
├── data/
│   ├── raw/            <- never edited, never overwritten
│   └── clean/          <- produced by your scripts
├── R/                  <- scripts
├── output/             <- figures, tables, saved models
└── report.Rmd

The data/raw rule is worth taking seriously: never modify a raw data file, not in R and certainly not by opening it in Excel and saving. Cleaning happens in code that reads from raw/ and writes to clean/, so that the transformation is visible, repeatable, and reviewable. A cleaned file with no script behind it is an assertion, not evidence.

One further nicety: file.path() joins path components with the right separator for the operating system, which spares you a class of Windows-versus-everyone-else bugs.

Exercise: a path that travels

A teammate’s script contains

dat <- read.csv("/Users/dana/Desktop/proj/data/survey.csv")

You have opened the project, so the working directory is already the project root, and the file sits in a data folder inside it. Build the path R should be given—as a character string—using file.path() rather than typing the separator yourself.

file.path(folder, filename)

which gives "data/survey.csv". Writing paste0(folder, "/", filename) happens to give the same string, but file.path() says what you mean and picks the separator for the platform.

Packages

Base R is deliberately small. Almost everything else arrives as a package, and nearly all of them come from CRAN.

There are two distinct acts, and confusing them causes a specific and very common failure.

Installing downloads the package onto your computer. You do it once per machine, and it is a setup act performed by a person:

install.packages("ggplot2")     # in the CONSOLE, not in your script

Loading makes an installed package’s functions available in the current session. You do it every session, and it belongs at the top of the script:

library(ggplot2)

Put install.packages() in a shared script and you force a reinstall on every run, require a network connection, risk silently upgrading a dependency mid-analysis, and occasionally stop the script dead on a prompt. Keep it in the console.

Two more points.

:: reaches into a package without loading it. stats::median(x) calls median from stats explicitly. This is useful when two packages define the same name—loading dplyr masks stats::filter, and R tells you so at load time in a message most people learn to ignore. When a function behaves nothing like its documentation, suspect masking and qualify the name.

library() errors, require() warns. Use library() in scripts. If the package is missing you want to be told immediately and loudly, not thirty lines later when a function is not found.

What Belongs at the Top of a Script

A teammate opens a shared analysis script with this at the top:

install.packages("ggplot2")
library(ggplot2)
setwd("/Users/dana/Desktop/project-final-v3")

Which criticism is the most serious for a script that other people have to run?

Both install.packages and setwd tie the script to Dana’s machine, and each does so in a different way.

setwd("/Users/dana/Desktop/project-final-v3") fails outright for everyone else—that directory does not exist on your computer. A hard-coded absolute path is the most reliable way to make an analysis unrunnable. The alternative is an RStudio Project: open the .Rproj file and the working directory is already the project folder, so every path in the script can be written relative to it, like read.csv("data/survey.csv"). Those paths work on every machine that has the folder, which is the whole point.

install.packages is more subtle, because it does not fail—it does something worse. It reinstalls the package every single run, needs a network connection, can silently upgrade a package to a version that changes your results, and on some systems triggers a prompt or a compile that stops the script dead in the middle. Installing is a one-time setup act performed by a person; loading is what a script does. Keep install.packages() in the console, or in a clearly marked setup file that nobody sources by accident.

The other options are wrong on the facts. install.packages does not require the package to be loaded—loading something you have not installed is the impossible direction. And require() is not the “script” form: it returns FALSE with a warning instead of stopping, so a missing package lets the script continue and fail later, somewhere confusing. In a script you want library(), which fails immediately and tells you why.

The workspace, and why you should refuse it

By default, R offers to save every object in memory to a hidden .RData file when you quit, and to reload it when you start. This sounds helpful and is the deepest source of irreproducibility in a beginner’s workflow.

With it on, your session at 9 a.m. contains everything from yesterday. Your script can reference an object it never creates and appear to work indefinitely. You will discover this at the worst possible time.

Turn it off now. Tools → Global Options → General:

  • Restore .RData into workspace at startup—unchecked
  • Save workspace to .RData on exit—Never

Then adopt the habit that makes the setting redundant anyway:

Restart R and run from the top

Several times a session, and always before you push or submit: Session → Restart R (Cmd/Ctrl+Shift+F10), then run your script from line 1.

Note that rm(list = ls()) is not a substitute. It clears objects but leaves loaded packages, changed options, and anything attached to the search path. Only a restart gives you the session your reader will have.

If it runs clean from an empty session, it will run for someone else. If it does not, you have just found a bug that was going to surface later, in public.

Getting help

You are allowed the documentation in every lab and exam in this course, so learn to read it.

?mean            # help page for a function you can name
??"linear model" # search help text when you cannot
args(round)      # just the arguments and their defaults
example(seq)     # run the examples from the help page

A help page has a fixed structure, and two sections repay attention out of proportion to their length:

  • Usage shows the argument order and every default. Most surprises live in a default you did not know existed—mean(x, trim = 0, na.rm = FALSE) tells you at a glance that missing values are not dropped unless you say so.
  • Value says what the function gives back, which is exactly what you need to know before writing the next line.

The two functions to reach for when an object surprises you:

str() is the single most useful diagnostic in R. Run it on every object you did not build yourself, and on every data frame the moment you read it in. It answers “what actually is this?” in one line per column, and it is where you catch a numeric column that was silently read in as text.

Exercise: find it yourself

Below is an object of the sort a modeling function might hand back. Nobody has told you what is inside it. Run str(fit) first, then return the slope coefficient on hours—as a single number.

The point of this exercise is the first step, not the second. Reading an unfamiliar object is a skill you will use every week of this course.

fit$coefficients[["hours"]]

fit[["coefficients"]]["hours"] also works and keeps the name attached. Double brackets drop the name and give you a bare number, which is usually what you want when the value is going into a sentence.

Errors, warnings, and messages

R has three severities and they are not interchangeable.

An error stops execution. Errors are the friendly ones: nothing further happens, and the message usually names the culprit.

A message is informational—the note about masked objects when you load a package, for instance. Harmless.

A warning is the dangerous category. R tells you something questionable happened and carries on with a value. If you are running a long script or knitting a document, the warning scrolls past and you are left holding a number that was quietly compromised.

Two entries could not be converted, so R produced NA for them and warned. It did not stop. Everything downstream inherits those NAs, and if somebody has written na.rm = TRUE further along, they will silently disappear.

Exercise: count what you lost

Before dropping anything, you should always be able to say how much you are dropping. Using raw from the setup, return the number of entries that failed to convert to a number.

sum(is.na(as.numeric(raw)))

which is 3. Note that is.na() is the right test here and == NA would not be—that trap gets its own section in An R Refresher.

How people break their own setup

A short taxonomy, drawn from previous cohorts. All four are avoidable and all four will happen to somebody in this room.

  1. The script that depends on the console. Covered above. Fixed by restarting R and running from the top.
  2. The absolute path. setwd("/Users/me/Desktop/...") at the top of a script. Fixed by using a Project and relative paths.
  3. The half-installed package. library(x) errors, so the student runs install.packages("x") inside the script, which then fails partway on a machine with no compiler—and the error message is about a C header file, which is genuinely frightening the first time. Fixed by installing in the console, once, and reading which package actually failed.
  4. Two copies of the project. One in Downloads, one in Documents, both open in different windows, edits landing in whichever was clicked most recently. This is what Git prevents, and it is why Reproducibility: RMarkdown and Git exists.

None of this is about being organized as a personality. It is about arranging things so that being disorganised is not fatal.

Summary
  • R computes; RStudio drives R. Install R first.
  • The console changes your session; the script is the record. Anything with <- goes in the script.
  • Use an RStudio Project and relative paths. Never setwd() to an absolute path.
  • Never modify a raw data file; clean in code, from data/raw to data/clean.
  • install.packages() once, in the console. library() every session, at the top of the script.
  • Turn off workspace saving and restoring. Restart R and run from the top, often. rm(list = ls()) is not a restart.
  • str() on every object you did not build. Read the Usage and Value sections of a help page.
  • Errors stop you; warnings hand you a compromised value and let you carry on. Warnings are the ones that hurt.
