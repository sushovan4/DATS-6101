Importing Data


27 minutes

Importing looks like the least interesting thing in this course. One function call, one line, done. In practice it is where a surprising share of wrong analyses are born, because read.csv makes a series of guesses about your file—where the header is, what separates the fields, what each column’s type is, what counts as missing—and it does not tell you what it guessed. It just hands you a data frame that looks fine.

The discipline of this section is short and it is not negotiable: after every import, look at what you got, before you use it.

About the code on this page

The cells here run R in your browser, and the browser has no access to your hard drive. So instead of reading a file that already exists, each example writes a small file into a temporary location and then reads it back. That keeps the read.csv calls completely honest—they really are parsing text out of a file—while letting you edit the file’s contents and re-run to see what changes. tempfile() invents a filename nobody else is using; writeLines() writes the lines you give it.

id came in as int, and the values are 7, 8, 9. The leading zeros are gone, permanently, and R did not consider this worth mentioning. If those ids are keys you later join on, or zip codes, or account numbers, or anything else where 007 and 7 are different strings in some other system, the damage is done at line one and shows up in week four as a join that silently drops rows.

The general shape of the problem: read.csv infers the type of each column from its contents. If every value in a column parses as a number, you get a number, and any information carried by the text form—leading zeros, a distinction between 01 and 1, a phone number’s formatting—is discarded.

What read.csv actually does

read.csv is read.table with some defaults pre-set. The ones worth knowing:

Argument Default in read.csv What it controls
header TRUE Is the first line column names?
sep "," Field separator
quote "\"" What wraps a field containing a comma
dec "." Decimal mark
na.strings "NA" Which text becomes NA
stringsAsFactors FALSE Do text columns become factors?
strip.white FALSE Trim spaces around unquoted fields
comment.char "" Text after this is ignored
check.names TRUE Make column names syntactically valid
colClasses NA Force column types
skip 0 Lines to discard before the header
nrows -1 Stop after this many rows
fileEncoding "" Character encoding of the file

Two of these deserve their own paragraphs.

stringsAsFactors

Before R 4.0.0, released in April 2020, this defaulted to TRUE, and every text column silently became a factor—R’s type for a categorical variable, stored internally as integer codes plus a lookup table of levels. This caused so much grief that changing the default was one of the headline items in that release.

You are on a modern R, so text stays text and you may reasonably wonder why this matters. It matters for two reasons. First, a great deal of code and a great many Stack Overflow answers on the internet were written before 2020, and an AI assistant trained on that corpus will occasionally hand you code that assumes the old behavior. Second, factors have not gone anywhere—you will create them deliberately, and read.csv(f, stringsAsFactors = TRUE) still exists—and the classic factor trap in Cleaning and Reshaping is one of the sharpest silent failures in R.

check.names

R makes column names syntactically valid by default, which means anything that is not a letter, digit, or dot becomes a dot, and names starting with a digit get an X in front.

Median Income ($) has become Median.Income...., which is ugly but usable. The reason to know about it is that check.names = FALSE preserves the originals, and you then have to refer to them with backticks, as in d$`Median Income ($)`, which is why most people accept the mangling and rename the columns explicitly instead:

Renaming to short, lower-case, underscore-separated names on import is a habit worth forming. It costs one line and it makes the next three weeks pleasant.

What a messy file actually looks like

Real exports are not four tidy lines. Here is a file of the sort that arrives from a survey platform or an agency portal: a couple of provenance lines above the header, a missing value written as N/A, and an empty cell.

Read that again. No error. No warning. A data frame with six rows and two columns, and a straight face.

Here is what happened. comment.char is "" in read.csv, so # is not special—it is just a character. The first line therefore became the header, and because that line happens to contain a comma (“survey, export”), R concluded the file has two columns. The data rows have three fields each, so R decided the extra leading field must be row names, and quietly used the city names for that purpose.

Every value in the file is still on screen somewhere, which is what makes this so dangerous: nothing looks empty. It looks like data. If your next line had been nrow(bad) you would have got 6, which is even close to the truth.

Delimiters that are not commas

CSV is a family, not a format. European exports often use ; because the comma is the decimal mark; tab-separated files are everywhere in bioinformatics; and pipe-delimited files turn up in banking.

One column named city.pop, with values like "Austin;961855". Nothing errored. If you had not looked, you would have a data frame with the right number of rows and one useless column.

R also ships read.delim (tab-separated) and read.csv2 (semicolon separator, comma decimal mark) as pre-configured wrappers, but read.csv with an explicit sep and dec is clearer about what you assumed.

Encodings, briefly

A text file is bytes; an encoding is the agreement about which bytes mean which characters. When the agreement breaks you get Ã© where é should be, or a column name that starts with an invisible character and never matches names(d) == "city".

Three things worth knowing.

UTF-8 is the modern default and what you should ask for whenever you control the export. read.csv(f, fileEncoding = "UTF-8") states it explicitly.

Excel on Windows writes a BOM. Files exported from Excel as “CSV UTF-8” begin with three invisible bytes marking the encoding. R reads them as part of the first column name, so names(d)[1] looks like city and is not equal to "city". The cure is fileEncoding = "UTF-8-BOM". If a name comparison is mysteriously failing on the very first column, this is why—check with nchar(names(d)[1]).

Older exports are often Latin-1. fileEncoding = "latin1" handles most Western European legacy files.

The diagnostic habit: if any text in your data frame looks wrong on screen, the problem is almost certainly encoding and almost certainly at import, not something to patch downstream with gsub.

The inspection ritual

Five calls, every time, before you trust anything.

What each one is for:

  • dim—do you have the number of rows and columns the source claimed? A file that should have 50 states and has 51 has a “United States” total row in it, and every mean you compute will be wrong.
  • str—the single most useful function in R. Types, and the first few values of each column. This is where you catch chr where you expected num.
  • head—do the first rows look like data, or like a second header line?
  • summary—ranges. This is where -99 in the score column is visible as a minimum, and where you notice an age of 999 or a price of 0.
  • sapply(d, class)—a compact list of types when there are too many columns for str to be readable.

summary(big) above shows Min. :-99.00 for score, on a variable that is otherwise between 2.9 and 5.0. That is a sentinel value, it is Cleaning and Reshaping’s subject, and you found it in four seconds because you looked.

Exercises

Exercise: get past the metadata

The file f has two provenance lines above the header. Read it correctly and return its dimensions.

d <- read.csv(f, skip = 2)
dim(d)

skip discards lines before R looks for the header, so the third line becomes the column names. An alternative here is comment.char = "#", which works because these particular junk lines happen to start with #; skip works regardless of what the junk looks like.

Exercise: make missing actually missing

The file f writes missing scores as N/A. Read it so that mean_score comes back as a numeric column, and return its mean over the non-missing values.

d <- read.csv(f, na.strings = c("NA", "N/A", ""))
mean(d$mean_score, na.rm = TRUE)

About 4.067. Listing the empty string as well is defensive: it changes nothing for a numeric column, where an empty field already becomes NA, but it matters enormously for text columns, where an empty field otherwise arrives as ""—a perfectly valid string that is.na() will never flag. Cleaning and Reshaping has more on that.

Exercise: keep the leading zeros

f holds a zip code column. Read it so the zip codes survive as written, and return the first one.

d <- read.csv(f, colClasses = c(zip = "character"))
d$zip[1]

"02134". The failure this prevents is nasty because it is geographic: zip codes with leading zeros are concentrated in the Northeast, so an analysis that loses them does not lose a random 8% of rows—it loses New England, and any regional comparison it then reports is wrong in a patterned way that looks like a finding.

Check yourself

A CSV has a column score whose three values are 4.1, N/A, and 3.7. You read it with read.csv(f) using every default, then run mean(d$score, na.rm = TRUE). What happens?

It returns NA and warns argument is not numeric or logical: returning NA.

The chain of events is worth tracing. read.csv scans the column, finds the text N/A, and concludes—correctly, given what it was told—that this column is text. Nothing in the column is an NA value, so na.rm = TRUE has nothing to remove and does exactly nothing. mean is then handed three strings, declines to average them, and returns NA.

Notice which part is dangerous. The warning is not the danger; the warning is R being helpful. The danger is that a script with fifty lines in it prints warnings you scroll past, and NA then flows into everything downstream. The fix is at import: read.csv(f, na.strings = c("NA", "N/A", "")) turns the text into a real NA, the column comes back numeric, and na.rm = TRUE finally has something to do.

Beyond CSV, in one paragraph

Base R reads delimited text and .RData; everything else needs a package. Excel files: readxl. Stata, SPSS and SAS: haven. JSON: jsonlite. Databases: DBI with a driver. Large CSVs where read.csv is too slow: data.table’s fread, or readr’s read_csv, which also declines to mangle your column names and prints the types it guessed. We will meet readr when we get to the tidyverse; for now, everything you need is in base R, and knowing what read.csv does with a file is the foundation for understanding what the fancier readers are doing differently.
